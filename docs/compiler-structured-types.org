* Current baseline
The most recent inspection found a working scalar compiler/evaluator with modules,
source diagnostics, reusable evaluation, and native generation through direct
LLVM bindings. The initial types are unit, bool, and i64. Both paths consume the
same checked representation.

The accepted input uses expanded core declarations such as %function, %import,
and %export. Base surface declarations are not core built-ins. Existing let and
if are unprefixed. Follow projects/compiler/AGENTS.md when extending this contract.

The focused verification performed during that inspection passed:
- 33 compiler acceptance checks and 22 regression tests.
- 14 shared fixtures through evaluation and native execution.
- Reader, allocation, evaluator-reuse, and execution-limit tests.
- 8 LLVM binding checks.

These are historical results, not verification of the proposed structured types.

* Design direction
Add concrete, immutable structured types before generics. Preserve the same value
semantics in evaluation and native execution.

Follow existing Verona conventions for product/sum/tuple declarations,
construction, field access, and matching. Inspect docs/API.md and existing source
before choosing exact core forms. Keep expanded declarations distinct from Base
surface syntax; no new concrete syntax was finalized in this discussion.

* Type declarations and identity
Resolve type declarations before checking function bodies.
- Assign stable nominal type IDs to products and sums.
- Give tuples structural identity based on their ordered element types.
- Reject duplicate fields or cases and unknown component types.
- Define type and constructor visibility across modules.
- Initially reject recursive layouts, including indirect cycles.

Recursive types behind pointers are later work. Decide whether forward references
between nonrecursive declarations are supported and implement cycle checking
accordingly. Do not confuse declaration IDs with existing scalar type IDs or
silently invalidate the evaluator's current type representation.

* Products and tuples first
- Products have named fields and nominal identity.
- Tuples have positional fields and structural identity.
- Check constructor arity and component types exactly.
- Resolve field access statically to a component index and type.
- Keep values immutable initially.
- Support composition of nonrecursive structured types as representations allow.

Settle empty/single-element tuples, empty products, tuple access syntax, and
construction evaluation order explicitly. Preserve established left-to-right
evaluation for constructor operands.

* Tagged sums
Represent a sum value as a case tag and its payload.
- Associate each constructor with a particular nominal sum and case ID.
- Check payload arity and types.
- Support zero-payload and payload-bearing cases.
- Resolve constructors through the expected sum type or explicit qualification.
- Diagnose ambiguous constructor names rather than selecting by declaration order.

Expected-type propagation may require extending the current checker. Exact
constructor qualification and inference rules remain to be designed.

* Initial pattern matching
Start with sum-case patterns containing local payload bindings, plus a wildcard.
- Resolve each pattern against the scrutinee's sum type.
- Evaluate the scrutinee once and select one branch at runtime.
- Scope payload bindings to their branch.
- Check every branch, including branches not selected during execution.
- Require identical result types across branches.
- Require exhaustive coverage.
- Reject duplicate cases and unreachable arms.

Defer guards and nested patterns. Specify duplicate payload-binding rules,
wildcard ordering, and zero-case sums before implementation. Initial matching
does not require general destructuring of products or tuples.

* Evaluator representation and ownership
Extend values from tagged scalars to scalars plus handles into immutable aggregate
storage. Per-run ownership is the starting suggestion, not a requirement to use
one allocation strategy for all storage.

- Copying a language value preserves its contents semantically.
- Immutable backing storage may be shared within its valid lifetime.
- Aggregate values returned from calls must survive the callee's frame cleanup.
- Aggregate results must remain valid until the owning evaluator outcome is destroyed.
- Cleanup must release retained result storage on success and failure.
- Repeated runs must not retain stale handles or leaked storage.

Use stable indices/handles if aggregate arrays can move. Do not retain pointers
into growable storage. Define how aggregate arguments borrowed from callers are
validated and retained; the current scalar-only API cannot be assumed sufficient.

The first design decision is aggregate ownership across function returns and
evaluator outcomes. Settle it before extending execution.

* Native representations
- Use LLVM structs for products and tuples.
- Use a case tag plus payload storage for sums.
- Calculate payload size and alignment using the selected target layout.
- Document the private internal ABI.
- Test construction, extraction, calls, returns, and matching before native
  interoperability.

Do not assume all payloads have the size or alignment of i64. Correctly handle
unit/empty structures and nesting. Extend the LLVM binding subset as required
after inspecting current bindings and pinned headers.

Avoid exposing internal sum layouts as a C ABI in this milestone. Native C
interoperability remains separate work.

* Shared checked representation
Represent resolved constructors, field accesses, and matches explicitly with:
- Concrete type IDs.
- Product field indices or sum case IDs.
- Payload binding identities and typed branch bodies.
- Source spans and relevant declaration locations.

Both backends consume this analyzed output without repeating constructor lookup,
field lookup, or exhaustiveness decisions.

* Structured result reporting
Extend the shared fixture/harness protocol to encode structured values with
their type, case where applicable, and recursively encoded contents.

Choose a stable unambiguous encoding shared by evaluator and native reporting.
Compare full structured values rather than reducing all fixtures to an integer.
Keep successful values distinct from language failures and driver/tool failures.
Extend the current nullary-i64 CLI/test entry restrictions deliberately rather
than assuming the existing harness already supports aggregates.

* Focused validation
- Nominal distinction between products/sums with identical shapes.
- Structural equality of tuple types by ordered component types.
- Constructor arity/type errors and ambiguous case names.
- Field lookup and private type/constructor visibility.
- Direct and indirect recursive-layout rejection.
- Nested aggregates and aggregate arguments/returns.
- Left-to-right construction and single scrutinee evaluation.
- Payload binding scopes, duplicate cases, missing cases, and unreachable arms.
- Mismatched match-branch result types.
- Zero-payload cases and unit-containing structures.
- Native tag/payload size and alignment.
- Returned aggregate lifetime, allocation failures, and repeated-run cleanup.
- Full structured-result parity across evaluator and native code-generation levels.

* Decisions to settle first
1. Aggregate ownership across calls, outcomes, and borrowed API arguments.
2. Exact core declaration, construction, access, and match syntax.
3. Type identity/visibility and expected-type constructor resolution.
4. Checked-node and runtime-value extensions.
5. Native layouts, LLVM binding additions, and structured result encoding.

Resolve details incrementally. The user prefers short steps and gathering further
information as implementation proceeds.

* Implementation decisions (2026-11-01)
The concrete core now uses %type products/sums, tuple construction/type syntax,
field and tuple-get access, and match with case payload names or a final wildcard.
Forward nonrecursive layouts work; empty products and empty/singleton tuples work;
empty sums and layout cycles are rejected. Type exports expose constructors.
Case qualification is Type:Case or module:Type:Case; expected types guide cases
through returns, annotations, arguments, components, conditionals and match arms.

Scalar type IDs remain 1–3. Nominal descriptors and interned structural tuples
use stable tape IDs plus four. Checked construction/extraction/match nodes retain
concrete types, field/tag indices, case identities and branch-local binder IDs.

Evaluator outcomes own immutable aggregate storage with one-based index handles.
Calls share handles inside a run; run-with-aggregates copies and validates borrowed
storage from the same checked program before execution. Destroy every outcome.

Native products/tuples are LLVM structs. Sums use a tag followed by a typed struct
for each case, rather than overlapping byte storage. LLVM computes all target
sizes and alignments, including empty/nested payloads. This intentionally larger
private ABI avoids guessed payload layout; compact unions remain an optimization.

The README defines the recursive typed result protocol and the deliberately
expanded nullary entry contract. Shared fixtures compare complete structured
results through evaluation and native -O0/-O2 execution. Generics, guards, nested
patterns, pointer recursion and native interoperability remain deferred.
