#+DATE: 2026-10-30
#+STARTUP: overview

* Purpose and handoff
This document records the name-resolution and type-checking recommendations
accepted by the user for a compiler and evaluator written in Verona.
Load it alongside:
- [[file:compiler-in-verona.org][Initial compiler and evaluator scope]]
- [[file:compiler-foundations.org][Foundations and allocation strategies]]

The checker implementation and validation are recorded below.
Read repository instructions before implementation, including AGENT.md and
/Users/dias/.codex/RTK.md. Prefix shell commands with rtk.

* Goal
Produce a resolved, typed program representation shared by the evaluator and
compiler. Neither execution path should repeat name lookup or type checking.

#+begin_example
Language syntax -> collect function signatures -> resolve/check bodies
                -> resolved, typed program -> evaluator or LLVM lowering
#+end_example

Check every function body, including functions that execution never reaches.
Do not execute or generate native code when semantic errors remain.

* Initial scope
- Types: unit, bool, i64.
- Explicit parameter and return types on named functions.
- Inferred types for immutable local bindings.
- Direct function calls, including recursion.
- Conditional expressions, integer arithmetic, and integer comparisons.

Defer implicit conversions, overloading, general type inference, generics,
protocols, and first-class function values for this initial checker.
The implementation itself may use existing Verona features beyond this subset.

* Collect signatures before bodies
1. Register all top-level function names with stable FunctionId values.
2. Resolve parameter and return annotations against the supported types.
3. Store signatures and declaration spans.
4. Reject duplicate function names and duplicate parameter names.
5. Resolve and check bodies against the collected signatures.

This supports forward calls and mutually recursive functions without inferring
their signatures from their bodies.

* Lexical name resolution
- Assign stable BindingId values to parameters and local bindings.
- Maintain lexical scopes and search the nearest scope first.
- Allow inner bindings to shadow outer bindings.
- For sequential local bindings, check each initializer before introducing its
  binding, so later initializers may refer to earlier bindings.
- A new binding does not refer to itself in its initializer. An outer binding
  with the same spelling remains visible there when applicable.
- Store resolved IDs in the output rather than relying on identifier spellings
  during execution.

The exact local-binding syntax and same-scope duplicate-binding policy still
need to be settled. Also specify how local names interact with function and
primitive names; do not accidentally allow resolution to depend on which
execution path is used.

* Type rules
| Expression          | Rule                                              |
|---------------------+---------------------------------------------------|
| unit                | Type unit                                         |
| true or false       | Type bool                                         |
| Integer literal     | Checked i64 value                                 |
| Local reference     | Type of its resolved binding                      |
| Direct call         | Arity and argument types match its signature      |
| Conditional         | Condition is bool; branch types are identical      |
| Integer arithmetic  | Operands and result are i64                        |
| Integer comparison  | Operands are i64; result is bool                   |
| Function body       | Body type matches the declared return type        |

Require exact type equality. Do not insert numeric conversions.
Both conditional branches are checked, although execution selects only one.
Exact primitive names, arities, supported operators, and equality on bool/unit
remain to be specified; do not infer additional operations from this table.

* Integer literals
Convert the spelling preserved by the reader into a checked i64 value here.
- Accept the minimum signed i64 value without overflowing an intermediate
  signed positive magnitude.
- Reject out-of-range values with a diagnostic at the literal's source span.
- Keep lexical validity in the reader and numeric range validity in this phase.

Runtime arithmetic follows the initial plan: wrapping integer arithmetic,
with runtime failures for division by zero and signed division overflow.
Type checking does not replace those runtime checks.

* Typed output
Each typed expression carries:
- Its concrete type.
- Its source span.
- Resolved BindingId or FunctionId where applicable.
- Explicit primitive operation where applicable.
- References to its typed child expressions.

Each function carries its signature, parameter binding IDs, declaration span,
and typed body. Keep source spans for relevant identifiers and declarations so
diagnostics can show both the use and the origin of an expectation.

Use the foundation plan's stable IDs and allocation strategies. Avoid pointers
into growable arrays. Concrete type layouts and module boundaries remain design
work; this document does not prescribe an implementation data structure.

* Diagnostics and recovery
Report:
- Unknown names and unknown type annotations.
- Duplicate functions and duplicate parameters.
- Incorrect argument count or argument types.
- Non-boolean conditions.
- Mismatched conditional branch types.
- Incorrect primitive operands.
- Function-body/return-type mismatches.
- Integer literals outside the i64 range.

Point to the offending expression and, where useful, the declaration establishing
the expected type. Include expected and actual types where available.

Continue checking independent functions after errors. Use an internal error
marker to suppress cascading errors within invalid expressions. This marker is
not a user-visible type and must never reach executable typed output.
Do not fabricate a valid signature for an invalid declaration merely to continue
checking; track invalid declarations explicitly.

* First milestone and validation
Successfully resolve and check factorial and mutually recursive functions.
Use focused cases for:
- Forward calls and recursion.
- Nested scope lookup and shadowing.
- Sequential binding visibility and initializer lookup.
- Unknown names and duplicate declarations/parameters.
- Incorrect call arity and argument types.
- Non-boolean conditions and mismatched branches.
- Incorrect function return types.
- Integer boundaries and out-of-range literals.
- Errors in unused functions.
- Source locations and suppression of follow-on diagnostics.

Verify typed output contains resolved IDs and concrete types suitable for both
execution paths. Execution must be blocked whenever semantic errors remain.

* Decisions before implementation
1. Settle the local-binding and conditional syntax.
2. Finalize shadowing, duplicate-local, and namespace rules.
3. Specify primitive names, signatures, and supported operations.
4. Specify main's signature and its mapping to native process exit status.
5. Define concrete symbol tables, typed nodes, and diagnostic interfaces.

Resolve these incrementally. The user prefers short steps and gathering
further information as implementation proceeds.

* Implementation record
The existing =projects/compiler/src/core.check.vrn= checker now supports inferred
=(let ((NAME VALUE) ...) BODY)= bindings, retaining optional exact annotations
=(NAME TYPE VALUE)= for compatibility. =if= and expanded =%function=/typed
integer primitives retain the established core conventions. Same-list duplicates
are rejected; initializers see earlier and outer bindings, and locals shadow
function names in call position with a not-callable diagnostic. The primitive
set remains binary i64 arithmetic (+, -, *, /) and comparisons (=, <, <=, >, >=),
without bool/unit equality. =main= remains nullary i64, with low-eight-bit native
process status.

The source-aware checked tape remains the shared typed representation. Stable
tape indices identify functions, parameters, locals, and child expressions;
checked binding nodes now record their initializer IDs for both execution paths.
Signatures are collected before bodies. Invalid declarations are explicitly
marked with kind 10 and type zero; calls do not fabricate valid signatures.
Type zero is an internal error marker and is never executed or lowered.

Semantic diagnostics accumulate across independent functions and expressions,
suppress dependent type mismatches, and include expected/actual types plus
origin notes for call parameters, annotated locals, return annotations, and
conditional branches. Malformed language forms recover at their containing
form; reader errors retain the reader's first-error contract. Semantic failure
blocks all execution/generation modes and releases the invocation arena.

The differential suite adds inferred scope/initializer/namespace cases and
multi-error recovery checks across check, eval, emit-llvm, and compile, including
invalid signatures, unused bodies, cascade suppression, and absent output files.

Verification in the pinned Nix development shell (loaded from the local checkout
with =nix develop path:.=): all 21 core FiveAM checks, all 16 differential/reader
integration groups, and all 85 LLVM checks pass. The broader frontend suite
passes 1326/1328 checks and reproduces only the two previously documented
=IDE-INSPECTION-SELECTS-EXPANSION-SUBTREES= failures. Both repository and compiler
submodule diffs pass whitespace checks.
