#+TITLE: Verona Compiler Roadmap
#+DATE: 2026-11-07
#+STARTUP: overview

* Current baseline

The maintained compiler is written in Verona and lives at the repository root.
Its source is in =src/=, its manifest is =verona.build=, and its tests are in
=tests/=. The Common Lisp implementation is archived separately in the
=verona-sbcl-compiler= repository and is no longer part of the build.

The local =build/verona= executable is the current development seed. It can read,
check, evaluate, compile, and rebuild the compiler. Generated binaries and test
evidence under =build/= are not source inputs and are excluded from version
control.

The Nix flake supplies LLVM/Clang 23, Python, Autoconf, and Automake on
=aarch64-darwin=, =aarch64-linux=, and =x86_64-linux=. The Make/Autoconf build
interface is being recreated for the root compiler. Projects under =projects/=
remain in their current locations and are outside the immediate cleanup work.

* Sources of truth

- [[file:../README.md][Compiler commands, syntax, representations, ownership, and limits]].
- =tests/compiler_contracts.json= for language, ABI, and CLI dispositions.
- =tests/compile_time_parity.json= for the compile-time helper API.
- [[file:compiler-boolean-operations.org][Boolean operation contracts]].
- =tests/test_core.py= for compiler regressions.
- =tests/shared/fixtures.json= for evaluator/native behavioral fixtures.

The archived compiler is historical evidence, not a build dependency. Current
Verona source, tests, and documented intentional differences define maintained
behavior.

* Current validation

Enter the pinned development shell:

#+begin_src sh
nix develop --offline path:.
#+end_src

Check the compiler implementation with the current seed:

#+begin_src sh
build/verona check src/core.cli.vrn \
  --module-path src \
  --module-path projects/base/src \
  --module-path projects/foundation/src \
  --module-path projects/libc/src \
  --module-path projects/llvm/src
#+end_src

Run the regression and shared suites:

#+begin_src sh
python3 tests/test_core.py build/verona
python3 tests/shared_suite.py build/verona
#+end_src

Rebuild the compiler through its root manifest:

#+begin_src sh
build/verona build verona build/compiler
python3 tests/test_core.py build/compiler/verona
python3 tests/shared_suite.py build/compiler/verona
#+end_src

The replacement Makefile should provide concise targets for these commands
without introducing a second implementation of build or test policy.

* Implemented compiler capabilities

- Source-aware reader, indexed syntax, modules, imports, aliases, exports,
  dependency collection, source-defined macros, and reader features.
- Lexical bindings, sequencing, calls, recursion, conditionals, pattern matching,
  diagnostics, and whole-program checking.
- Signed and unsigned integer widths, f32/f64, conversions, wrapping arithmetic,
  comparisons, bit operations, data literals, and u8 character literals.
- Products, tuples, sums, arrays, transparent aliases, opaque handles, pointers,
  mutable globals, function pointers, native calls, and C ABI adapters.
- Concrete generic overloads, constrained specialization, protocols, default
  numeric dispatch, and pointer equality.
- Compile-time syntax construction, collections, strings, arbitrary-precision
  arithmetic, conversion, compilation context, and isolated session state.
- LLVM construction, verification, IR printing, object emission, native exports,
  generated C headers, and executable/object/static/shared artifacts.
- Manifest builds, optimization levels, reader features, target triples, CPU and
  machine features, native link options, and default artifact paths.
- AArch64 and x86-64 target support for Darwin and Linux with 64-bit
  little-endian pointers.

* Next work

** 1. Restore the root build interface

Create the new Autoconf/Automake files around the self-hosted compiler. The build
must accept an explicit seed compiler, build =verona= from the root manifest, run
the Python and Verona test suites, and install the resulting compiler. Do not
restore SBCL, ASDF, CL-LLVM, or the archived IDE server.

Define how a fresh checkout obtains a compatible seed compiler. A local ignored
=build/verona= is sufficient for development but not for a reproducible source
release. The release process should either accept an explicit seed path or fetch
a versioned compiler artifact with a recorded hash.

** 2. Disposition retained language restrictions

Early return remains out of scope by decision. If revisited, implement never-type
checking, unreachable diagnostics, terminating LLVM control flow, evaluator
cleanup, and focused tests together.

The following restrictions still need an explicit retain-or-implement decision:

- Pattern guards, nested structured patterns, and product destructuring.
- Aggregate/computed constants and aggregate/runtime global initializers.
- Generic inference and changing-type recursive specialization limitations.
- Separate compilation and persistent compilation caches.

Character literals deliberately remain =u8= with explicit conversions rather
than adopting a distinct character type and implicit widening.

** 3. Finish compiler driver review

Review remaining CLI and artifact behavior against the contract inventory. Focus
on option validation, search and link ordering, failure cleanup, exported symbols,
headers, target facts, installation, and release behavior. Projects and package
management are deferred until the compiler build interface is stable.

** 4. Broaden native validation

Run native ABI, callback, shared-library, and compiler-rebuild tests on each
supported host. Foreign object inspection does not prove execution. New hosts or
architectures require target facts, layout, ABI classification, native execution,
and clear rejection tests.

** 5. Optional compiler improvements

Debug information, native stack reporting, an LLVM IR optimization pipeline,
closures, bytecode/JIT execution, tail-call optimization, and native calls from
the evaluator remain separately scoped work. None is required to maintain the
current self-hosted compiler.

* Design constraints

- Reader syntax and checked expressions remain separate. Evaluation and LLVM
  lowering consume the same resolved typed representation.
- Preserve source locations, left-to-right evaluation, lazy branches, wrapping
  integer behavior, failure ordering, and explicit ownership.
- Keep LLVM ownership in the backend and artifact/link policy in the driver.
  Invoke native tools with argument vectors, never shell command strings.
- Destroy owning success and failure values. Keep borrowed source, syntax, names,
  checked programs, regions, and native handles alive for their consumers.
- Maintain independent expected results in focused tests; backend agreement alone
  can conceal a shared frontend error.
- Keep generated outputs outside source control and record the seed compiler,
  toolchain, source revision, options, and hashes for release validation.

* Updating this document

Update this roadmap when scope or retained restrictions change. Do not append
historical implementation diaries; Git history records completed work. Keep the
current baseline, validation commands, and next actionable compiler work accurate.
