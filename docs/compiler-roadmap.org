** DONE 6. Specify the runtime evaluator's native-call boundary
The runtime evaluator checks native declarations but fails explicitly when
execution reaches a native call. It supports managed pointers, aggregates,
mutation, and calls to Verona functions; it does not execute native allocation,
file/process I/O, or arbitrary C calls. The macro evaluator is a separate syntax
execution layer; do not conflate these capability surfaces.

Decision: retain the explicit native-call failure. Existing ABI tests and the new
generated-native-symbol test check that evaluation rejects native execution while
compiled execution succeeds. No managed/native pointer bridge is introduced.

Any future native operations in interpreted execution need a separate contract. Keeping
the current restriction is a valid documented scope choice. If native execution
is required, define an explicit bridge: supported signatures, managed/native
pointer conversion, ownership, callbacks, target restrictions, and failure cleanup.
Do not pass managed pointer tokens to C as host addresses.

Completion: supported calls have focused ABI, lifetime, callback, and failure
tests; unsupported calls retain explicit outcomes and source traces. Shared
fixtures declare applicability, so unavailable native evaluation is never
mistaken for successful parity. This extension is not a prerequisite to the

* Design decisions to preserve throughout
** Shared analysis and representations
Reader syntax is separate from checked expressions. Both execution paths consume
the same resolved typed tape, with stable declaration/binder/type IDs and source
spans; neither backend repeats name lookup or type checking. Check unused bodies,
recover across independent semantic errors, suppress dependent cascades, and never
execute the internal error type. Keep macro expansion ahead of semantic checking.

Products and sums have nominal identity; tuples have structural identity.
LLVM computes actual target layouts. Private structured values use typed LLVM
structs and sum case storage; C objects use their separately specified layouts and
ABI conversion. Do not assume payload sizes or expose a private layout as C ABI.

Preserve left-to-right operand/argument/construction order, single scrutinee
evaluation, lazy branches, exact numeric types, wrapping integer operations, and
guarded invalid division. Observable failure order is part of the contract.

** Mixed allocation and ownership
Use indices across growable arrays. Keep source, syntax, names, checked program,
per-run frames/values, managed regions, and native handles alive for their clients.
Choose scratch/session arenas or reclaiming allocators by actual lifetime; avoid
retaining every old buffer during growth. Collections store shallow descriptors,
so nested resources need explicit cleanup.

Evaluator outcomes own aggregate/managed storage and traces. Returned values
survive callee cleanup; borrowed input storage is validated/copied according to
the API. Destroy success and failure outcomes. A checked program must remain
reusable after success, language failure, limit exhaustion, or allocation failure.
Test expired pointers, bounds, alignment, read-only literals, repeated runs, and
injected allocation failures. Release files/process/LLVM handles independently
of arena reclamation.

** Native backend and tool boundary
Use the Verona LLVM bindings for construction, verification, printing, and object
emission. Keep target-machine/module/builder ownership in the backend, and artifact
policy, native tools, output paths, and manifests in the driver. Pass argv vectors,
not shell strings. Retain temporary-object and argument-storage cleanup on every
outcome. Pin library sources through submodule revisions and host tools through
the Nix environment; record the actual linked LLVM and native tool configuration.

** Independent expectations and complete results
Keep focused reader, resolution, checking, expansion, ABI, and diagnostic tests
in addition to shared behavioral fixtures. Backend agreement alone can conceal
a common frontend error. Fixtures name source/modules, entry/arguments, and an
independent typed expected value or expected failure with relevant locations.

The current shared harness supports nullary main; arbitrary checked entries and
typed arguments have reusable-evaluator coverage. Extend harness applicability
explicitly before requiring new entry conventions. Encode full signed/unsigned
values, float bits, and nested aggregate type/case/component identity. Process
status is not a full-value protocol. Distinguish language, resource, tool, and
internal failures; native stacks need not match evaluator traces.

** Reproducible validation
The bootstrap command uses fresh A/B/C directories and the same selected source
snapshot. It records hashes, revisions/patches, tool paths/versions, target/ABI,
optimization, link settings, and relevant environment; it stops on failure or
input changes and retains diagnostics/IR. A uses manifest optimization 2; B/C
currently use explicit compile at -O0 with module paths and the LLVM dependency.
Manifest support is implemented even though the gate retains explicit commands.

Run each stage's evaluator and native suites before exact B/C comparison. Do not
normalize meaningful instruction, constant, control-flow, signature, or helper
differences. If exact equality fails, record behavioral/IR findings without
reporting the exact gate as passed. Broaden normalization only for explicitly
identified irrelevant metadata. Keep reproducibility status distinct from
behavioral coverage.

The project audit selects an explicit compiler, isolates source/output, records
provenance, checks fresh native libraries/headers, and validates intended negative
phases. Never substitute a host-built artifact or count a stale output as success.
See the audit guide for maintained policy and timeout/dependency behavior.
