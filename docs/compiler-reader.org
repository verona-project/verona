* Design direction
Separate reading S-expressions from interpreting language constructs.

#+begin_example
Source buffer -> tokens -> S-expression syntax -> language syntax
              -> name resolution -> type checking
#+end_example

The reader understands atoms and lists. A later syntax-lowering step recognizes
function declarations, calls, bindings, conditionals, and other language forms.
Do not combine reader parsing with name resolution or type checking.

* Initial lexical scope
Support:
- Opening and closing parentheses.
- Identifiers.
- Signed decimal integer literals.
- Whitespace.
- Semicolon comments extending to the end of the line.

Read true, false, and unit as identifiers; recognize their language meaning
during syntax lowering.

Defer strings, quoting, and reader extensions for the first version.
Exact identifier characters, whitespace rules, sign/token boundaries, and
non-ASCII handling still need to be specified before implementation.
In particular, distinguish an operator identifier such as - from a signed
integer literal such as -12.

* Source buffers and locations
Every token and syntax node carries a source span:
- File ID.
- Start byte offset, inclusive.
- End byte offset, exclusive.

Retain original source buffers while syntax, diagnostics, or borrowed spelling
references need them. Store a table of line-start byte offsets for each file
and calculate diagnostic line and column information from source offsets.

A list span includes its opening and closing parentheses. An atom span covers
its spelling. Decide and document the diagnostic column convention, newline
handling, and EOF span representation before writing location assertions.

* S-expression representation
Start with three node kinds:
- Identifier.
- Integer literal.
- List.

Store nodes in an array and refer to them through NodeId values. Store child
NodeIds in a separate array; each list records a start index and child count.
Represent top-level forms as a sequence of NodeIds.

Intern identifiers using the foundation support layer. Retain their source
spans even when multiple occurrences share an interned identifier ID.

Avoid retaining pointers into growable arrays. Node IDs and child indices must
remain valid when backing storage moves.

** Integer literals
Preserve the original spelling through its source span until numeric checking.
Do not force every literal through the reader implementation's signed integer
representation.

This allows later checking of overflow and the minimum signed integer value.
The reader checks lexical validity; numeric range validation belongs to the
later language/type-checking stages.

* Reader algorithm
Use an explicit parsing stack rather than native recursion for nested lists.

Each open parenthesis starts a frame containing:
- Its opening source location.
- Its pending direct child NodeIds.

On a closing parenthesis:
1. Verify that an open frame exists.
2. Append that frame's direct children together to the child-ID array.
3. Create a list node containing the resulting child range and full source span.
4. Append its NodeId to the parent frame, or to the top-level forms.

Nested list children may already have been stored elsewhere in the child-ID
array. Appending each completed list's direct children together preserves a
contiguous range for that list.

An empty list has a zero child count. EOF with open frames is an unclosed-list
error. An explicit stack avoids native parser recursion, but storage growth,
allocation failures, and any chosen resource limits still need handling.

* Language syntax lowering
Build a separate language syntax representation from the S-expression nodes.
Initially recognize the agreed core: named functions, direct calls, immutable
bindings, conditional expressions, and primitive values/operations.

Preserve spans when creating language nodes. Keep references to relevant
subexpression and identifier spans for precise later diagnostics.

The exact binding and conditional surface forms remain to be settled; consult
the initial plan and current Verona syntax before choosing them.

* Initial error behavior
Stop at the first reader error and return a structured diagnostic.
Initially cover:
- Unexpected closing parenthesis.
- Unclosed list at EOF.
- Invalid input byte under the chosen lexical rules.
- Malformed integer under the chosen token classification rules.

An unclosed-list diagnostic points back to its opening parenthesis.
Do not add error recovery in the first implementation.

Lexical classification must define when a token is an identifier versus a
malformed numeric token; do not reject identifier spellings accidentally.

* Allocation and ownership
Follow the mixed allocation strategy from the foundations plan.
- Source buffers and retained syntax need storage that survives their clients.
- Parser frames and temporary child buffers may use scratch storage.
- Copy retained data out of scratch storage before resetting it.
- Choose general allocation where repeated buffer growth should reclaim old
  storage rather than retaining all previous allocations in an arena.
- Keep interned-name ownership consistent with the compilation/session lifetime.

* Validation and first milestone
Use focused fixtures for:
- Nested and empty lists, plus multiple top-level forms.
- Whitespace, comments, and EOF boundaries.
- Identifier/operator and integer token boundaries.
- Integer boundary spellings, with range errors checked in the later phase.
- Unexpected closing parentheses and unclosed lists.
- Malformed input under the documented lexical rules.
- Deep nesting without native parser stack exhaustion.
- Exact token/node spans and diagnostic locations.

The first useful milestone is reading a factorial source file and printing its
S-expression syntax tree with source locations. Keep any debug tree traversal
from reintroducing an avoidable recursion limit in deep-nesting verification.

* Next decisions
1. Specify lexical rules and source-position conventions.
2. Define concrete span, token, node, child-range, and parser-frame types.
3. Choose module boundaries and integrate existing Foundation collections.
4. Implement tokenization and the stack-based S-expression reader.
5. Validate locations and errors before language syntax lowering.

Resolve details incrementally. The user prefers short steps and gathering
further information as implementation proceeds.

* Implementation record
The reusable =projects/compiler/src/core.sexpr.vrn= reader now provides token,
node, child-ID, top-level-ID, and line-start arrays. It uses explicit list frames,
interns identifiers through =core.names=, and returns structured first-error
diagnostics, including allocation failures. Decimal spellings retain their spans
without numeric conversion. The package README specifies the lexical, position,
ownership, and EOF contracts resolved during implementation.

=core.reader= adapts this representation to the existing language-analysis tape;
the checker, evaluator, and LLVM backend continue to share the checked tape.
Language analysis retains its resource limits independently of reading.
=verona-core read FILE= prints indexed syntax and source locations, including
factorial, without invoking language analysis. Its traversal also handles deep
nesting without a native recursive tree walk.

=make test-compiler-support= includes named reader structure/location/error and
allocation-failure tests. =make test-compiler-core= adds reader integration and
12,000-level/12,000-sibling checks alongside existing differential execution tests.
A dedicated language AST replacing the existing checked-tape frontend remains a
later migration; this change establishes the independent reader boundary first.

Verification: the 21 core FiveAM checks, all 13 differential/reader integration
groups, and all 14 named support/reader tests pass in the pinned Nix shell.
The broader frontend suite passes 1326/1328 checks and reproduces the two
previously recorded =IDE-INSPECTION-SELECTS-EXPANSION-SUBTREES= failures.
