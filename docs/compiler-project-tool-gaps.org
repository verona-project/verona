#+DATE: 2026-11-06
#+STARTUP: overview

* Scope and current status
The Verona compiler has passed the self-hosting gate: stages B and C are
byte-for-byte identical, and stages A, B, and C passed 87 core regressions and
47 shared fixtures each. Building every project tool is a separate milestone.

This checklist records the first blockers found while building the current
workspace's project manifests with the verified stage C compiler. Follow the
Common Lisp compiler's existing behavior when porting compiler features; the
Verona evaluator does not require implementing Common Lisp.

The original audit translated manifest settings into explicit =compile=
arguments. It did not exercise a self-hosted manifest reader or fall back to
the Common Lisp compiler. Existing host-built repository libraries were excluded.

The latest validation builds all 17 normal executables and seven libraries
directly from their manifests with =verona-core build=. Both intentional
negative fixtures fail at their intended phase. The compiler also rebuilds
itself through its own manifest; see the progress section for evidence.

Original audit results:
- Four of 17 normal executable targets built: =verona-core=, =calculator=,
  =echo-server=, and =llvm-tests=.
- Thirteen normal executables failed compilation.
- Two deliberate failure fixtures failed before their intended diagnostic.
- Seven library targets require artifact output support absent from the
  self-hosted executable-only CLI.

The rebuilt =-O2= compiler passed all 87 core regressions. The calculator
passed a =3+4= smoke check. LLVM bindings passed verification, diagnostic,
call, phi, and object-emission checks; the emitted object linked and returned
42. The echo server was built without starting its persistent network service.

These are observed first blockers, not a complete language-parity inventory.
Rebuild affected targets after each item; later failures may reveal more work.

* Implementation checklist
** DONE Port compile-time reductions
Implement =compiler:reduce= and =compiler:reduce-right= using the behavior in
[[file:../src/compiler.lisp][the reference compiler's compile-time helpers]]. These helpers construct syntax;
they do not execute the named runtime operation while expanding the macro.

For head =f=, initial form =z=, and forms =(a b)=:
- =reduce= produces =(f (f z a) b)=.
- =reduce-right= produces =(f a (f b z))=.
- An empty input returns the initial form.

Preserve the reference validation of the call head, proper list input, and
S-expression arguments. Keep symbol resolution and source locations intact.

Affected targets:
- =verona-fmt= and =verona-project=: =compiler:reduce-right=.
- =bounded-tests= and =foundation-example=: =compiler:reduce= in =testing:checks=.
- =formatter-tests= and =testing-smoke= also encounter these helpers after
  declaration support is addressed.

Completion check: focused expansion checks for order, empty input, and invalid
arguments, followed by rebuilding the affected tools and running their checks.

** DONE Support mutable global variables
Accept and lower the =%variable= declarations produced by =base:variable=.
Follow the reference compiler's rules for initialization, storage, reads,
assignment, address-taking, and module visibility.

Affected targets: =compiler-tests=, =formatter-tests=, =foundation-tests=,
and =testing-smoke=. Their first declaration failures include mutable test
state such as temporary paths, allocation counters, and evaluation budgets.
The current generic declaration diagnostic does not identify this gap clearly.

Completion check: validate initialization, mutation, address-taking, and
cross-module access as applicable to the reference behavior; then rebuild
and run the affected suites. Reduction support is also needed by their macros.

** DONE Port the compile-time state and data helpers used by generated declarations
The =macro-expansion= example initializes =models:types= using
=compiler:state-set!=, then reads it with =compiler:state-ref= and processes
the result using =nth= and =plist-ref=. Compilation currently stops at the
=state-ref= call.

Compare the full example against the reference compiler's compile-time
environment and state implementation. Establish which operations already work
and port those still missing, including state initialization and isolation
between compilations. Do not treat reaching one unsupported call as proof
that all earlier state operations behaved correctly.

Completion check: build and run =macro-expansion=, expecting output =42=,
and verify that independent compilations do not share mutable compiler state.

** DONE Support pointer equality through the default generics
The =bootstrap= tool compares =getenv= results using ====. After mutable global
support, =foundation-tests= also reaches pointer comparisons in its allocation
tracker and arena tests. The self-hosted compiler currently reports no matching
generic implementation for these calls.
Follow the reference compiler's pointer equality and inequality rules, including
compatible pointer types and null-pointer behavior; retain numeric dispatch.

Completion check: exercise pointer identity and inequality, reject incompatible
operands according to the reference rules, and build and run =bootstrap= with
the relevant environment variables both present and absent.

** DONE Reconcile character arguments in wc
=wc= passes =#\space= and =#\newline=, which have type =u8=, to its
=write-character= helper, whose argument is =i32=. The compiler reports the
type mismatch at those calls.

Characters remain =u8= in Verona. Check the helper's intended interface and
the reference conversion rules; adjust the helper or use explicit casts at
the C boundary as appropriate. This is an observed source compatibility issue,
not evidence that arbitrary implicit integer conversion should be introduced.

Completion check: build =wc= and exercise standard input, files, and selected
counts. Input =one two\nthree\n= should report two lines, three words, and
14 bytes with the default selection.

** DONE Align older examples with declaration expansion
=workflow= and =dynamic-library-client= use surface declarations without
importing Base. The compiler expects declarations such as =%function= after
macro expansion; surface declarations belong to Base.

Review these examples against the reference setup and repository input
conventions. Provide the appropriate Base imports and module paths, or use
expanded forms where the fixture is intentionally testing compiler input.
Do not add concrete surface aliases to the semantic checker to bypass expansion.

The IDE's two negative fixtures also stop at declaration handling:
- =analysis-failure= must reach the unresolved =missing-workflow-value= diagnostic.
- =link-failure= must pass analysis and reach the native linker, which must
  reject =verona_missing_library_for_workflow_test=.

Completion check: =workflow= runs and returns 7; both negative fixtures fail
at their intended phase with the intended diagnostic. The dynamic library
client additionally needs the artifact support below.

** DONE Add native library artifact output

| Kind           | Targets                                                    |
|----------------+------------------------------------------------------------|
| Static library | base, foundation, workflow-library, libc, verona-llvm, testing |
| Shared library | dynamic-library                                            |

Keep artifact selection and native tool invocation in the driver layer.
Library roots must not require =main=. Preserve exports, target-specific
filenames, and linking behavior; establish any object-output and header
requirements from the reference driver rather than guessing them.

Completion check: build all seven library targets, then link and run
=dynamic-library-client= against the freshly self-hosted shared library.
Do not satisfy that dependency using an existing host-built artifact.

** DONE Support manifest-driven builds in the self-hosted driver
The audit's external adapter is not an implementation of =verona.build=.
Port the reference driver's manifest handling so project builds can be invoked
directly through the self-hosted toolchain.

Cover the settings exercised by the current manifests: multiple named targets,
artifact kind, root module, manifest-relative module paths, native target,
optimization, version metadata, library paths, and libraries. Preserve the
reference behavior for other supported settings and invalid manifests as the
driver is ported. Native dependencies such as LLVM still require explicit
toolchain discovery and linking.

Completion check: build the projects from their manifests without manually
translating options, preserving isolation from existing output artifacts.

** Compile-time state and data helpers completed
The self-hosted macro evaluator now supports =compiler:state-ref=,
=compiler:state-has?=, =compiler:state-set!=, =compiler:state-remove!=,
=nth=, and =plist-ref=. State belongs to a compilation session, with snapshots
of stored and returned data. Qualified keys normalize module identities through
the invoking module's aliases, including qualified names nested inside lists.
Stored =nil= remains distinct from an absent key; list bounds, property-list
shape, duplicate keys, defaults, and invalid arities follow the reference rules.

source order, including statements emitted by macros. Statement results are
discarded as data. State and collection traversal consume the existing shared
evaluation budget.

generic specialization retain source identities and reuse cached expansions;
generated forms remain distinct even when their source spans match or one
argument is unquoted twice. This matches the reference compiler's once-per-source
expansion behavior without identifying forms by source offsets.

** Pointer equality completed

ordinary generic resolution. Operands must have exactly matching pointer types;
there is no implicit void-pointer conversion or integer-to-null coercion.

precedence. Pointer ordering remains unsupported by this fallback.

identities and offsets rather than managed handle IDs, retaining data-literal
origins across pointer arithmetic. Comparison does not dereference memory or
require aligned, live storage; reads and writes keep their existing checks.
Native callback adapters are shared per function, and external declarations
that name one C symbol retain one identity in the evaluator as well.

** Native library artifact output completed
=compile= now accepts =--emit object|executable|static-library|shared-library=,
with executable output as the default and an explicit =-o= output path.
Object and library roots do not require =main= or receive an entry wrapper.
Executable entry checks and =compile-report= behavior remain in place.

Explicit =native-export= declarations resolve local functions and validate
recursive C-compatible parameter/result types and unique C names across the
loaded graph. C ABI adapters expose those functions; ordinary module exports
and private functions remain hidden. Exported entry points reuse the existing
scalar, aggregate, and callback conversion machinery. Native function addresses
share the first exported adapter for that function.

Objects are emitted through LLVM, static libraries use =ar rcs=, and shared
libraries use PIC output and the reference platform linker flags. Library
headers describe scalar types, products, tagged sums, arrays, opaque handles,
pointer chains, callbacks, and explicit native export prototypes. Headers sit
beside their libraries with the final extension replaced by =.h=.
Native tool argument storage and temporary object cleanup cover success,
failed tools, and injected allocation failures. The dynamic-library example
now imports Base and its manifest includes Base's source path.

** Manifest-driven builds completed
The self-hosted CLI now implements
=build TARGET OUTPUT-DIRECTORY [--feature NAME ...]=. It reads the current
=verona.build= as source-located configuration data, without expansion or
evaluation. All declarations are validated before target selection, including
unselected targets. The parser checks required roots, unique target names,
option arities and value types, repeated singleton options, and unknown forms.

Module and library directories resolve relative to the manifest, preserving
order. Defaults, native libraries/frameworks, optimization levels 0 through 3,
version metadata, reader features, artifact filenames, and output directory
creation follow the reference driver. The existing compiler pipeline handles
the selected root and artifact. Successful builds print the artifact path.
The native tool selection honors the pinned =VERONA_LINKER= and =VERONA_AR=
settings, with the core-specific overrides retaining precedence.

Selected target facts reach every source reader and the C ABI classifier.
LLVM supplies data layout and pointer width before source analysis. AArch64
and x86-64 Darwin/Linux targets with 64-bit little-endian pointers are supported;
other architectures/layouts are explicitly rejected rather than compiled for
the host. Compiler-provided facts precede CLI and package reader features.
The configuration is per invocation and survives compile-time state/cache
updates. Target facts and feature handling live in a frontend-only module;
LLVM machine ownership stays in the backend, so reusable readers and the
compiler support suite acquire no LLVM dependency.
